# Native Android client (stage 1)

This Android client is Kotlin/Jetpack Compose with Room, SQLCipher and WorkManager. The GraphQL service exposes the branch's `str_cobro_adicional` as `extraCharge` so the new-card form can follow the same configuration as the PHP cartera.

## Build setup

Install JDK 17, Android SDK Platform 35 and Android Build Tools 35.0.0. The checked-in Gradle wrapper downloads Gradle 8.9. Set `ANDROID_SDK_ROOT` (or configure the SDK location in an untracked `local.properties`). From this directory:

```sh
./gradlew :app:testDebugUnitTest
./gradlew :app:assembleDebug -PGRAPHQL_ENDPOINT=https://api.example.invalid/graphql
```

The endpoint above is a placeholder, not a working service. Configure the deployed TLS GraphQL endpoint with `-PGRAPHQL_ENDPOINT=https://host/path`; the value is compiled into `BuildConfig.GRAPHQL_ENDPOINT`. Do not put credentials in Gradle properties, source files, or this documentation.

For a temporary physical-device test on a trusted private Wi-Fi, build the debug APK with the computer's current LAN address, for example:

```sh
./gradlew :app:assembleDebug -PGRAPHQL_ENDPOINT=http://192.168.1.53:3000/graphql
```

The debug manifest alone permits HTTP; the main manifest still disallows cleartext for non-debug builds. Use a test account only: credentials and API traffic are unencrypted over HTTP. Do not use this endpoint on public/shared Wi-Fi or in a release APK. The phone and computer must be on the same network, and the computer firewall must allow port 3000.

The app targets API 35, supports API 26+, and uses the Kotlin 2.0.21 / AGP 8.7.3 toolchain. Tests cover queue state transitions, idempotent operation identity, dependency readiness, retry decisions, GraphQL documents/DTOs, and the strict customer/credit/payment payload mappings (including payment signs and entity IDs).

## Server contract

`network/GraphQlDocuments.kt` is the single source for GraphQL documents and is aligned to `src/graphql/schema.ts` and `src/services/queries.ts`. Login passes an integer `companyId` and parses `token`, `expiresIn`, `user`, `company`, and `branches`. Branch IDs/customer IDs use GraphQL `Int`; GraphQL `ID` values accept their numeric JSON representation. The typed OkHttp client calls `login`, `me`, `branches`, `portfolio`, `customerById`, `customerByDocument`, `paymentHistory`, `syncChanges`, and `applyOfflineOperation`, plus `routeSettlement`/`settleRoute` for the Cuentas del día screen.

Portfolio pages use `nodes: Customer[]` with the schema's customer fields and embedded `credits`/`comments`, plus `snapshotCursor`, `nextCursor`, and `hasNextPage`. Payment history uses `amount`, `description`, `state`, `createdAt`, `updatedAt`, and `routeId`. `syncChanges` requires an `after` cursor and returns `nodes` containing `cursor`, `recordType`, `recordId`, `action`, `createdAt`, and JSON `payload`. The mutation accepts `OfflineOperationInput` and returns `operationId`, `status`, `entityId`, `data`, `eventCursor`, and `replayed`. `payload` is sent as JSON. The server remains authoritative.

The client does not implement or simulate backend validation. Keep documents and typed DTOs aligned if the schema changes. Server acknowledgements are interpreted only after the returned operation ID matches and the status indicates application; after acknowledgement, the client pulls changes from its saved cursor through the returned event cursor before advancing the queue.

## Offline behavior and local data

- First sign-in requires an online server login. The password is only held in UI memory while submitting and is never stored in preferences, Room, or the offline queue.
- Offline unlock uses the device's biometric or screen-lock credential to open the local app. It does **not** authenticate to the server or renew a token.
- Only the selected branch's portfolio-linked customer/card records, the customer fields needed by the typed update form, and fetched payment history are cached. A customer fetched by ID or document is also saved when explicitly opened. The app does not download the company's complete customer directory.
- The portfolio card shows the latest cached `tbl_descripcion` record by type and detail (payment, `c-Inicial`, initial installment, discount, interest, correction, or cancellation). Only `Abono` and `c-Inicial` authored by the signed-in user with `created`/`entregando` state have green backgrounds (`#4b965b`/`#1f5b2c`); unknown or other authors appear gray. The creator's first and last names are title-cased in the UI. Pending device-created payments still show their separate queue/synchronization status and are not presented as server-confirmed.
- Once a branch is chosen, the top bar title replaces "Créditos" with `username · str_tipo · str_codigo` preceded by a status dot (tap it to open sync settings): green when online with automatic sync running, orange when the server session expired, and red when offline or automatic sync is off or paused. "Créditos" remains only on login and branch selection.
- Under the top bar, every branch screen shows one totals line, `Abs: 10/260 · R: 11.250 · C: 500.000`, matching the web cartera (`view_ruta.recaudo` and the `sumRecaudoCreditos` worker) for the open route: **Abs** = cards with collected money / cards in the portfolio, **R** (recaudo) = Abono/Inicial/Cancelado movements in `created`/`entregando` state, **C** (créditos) = `dec_prestamo` of cards in `created`/`entregando`. It is computed in one pass over the cached cards and payments and only recalculated when those lists change; local pending abonos count immediately, since they are also cached as `created`.
- Below the portfolio search box, the "Cartera guardada" title and hint were replaced by a fixed 4 dp progress bar (no layout jump): indeterminate while the portfolio loads/syncs or an abono waits for server confirmation, otherwise it shows route progress (cards with collected money / cards).
- Under the progress bar, a pocket-cash line replaces the old usage hint: `Caja: X = B base + R abonos + O otro recaudo − G gastos − C créditos` for the open (not saved) route day. Abonos (R), seguros (added to O, as webgoez does) and new credits (C) come from the cached cards and update instantly; base, other income (`entrada-*` except `recaudo`/`diferencia`) and expenses (`salida-*` except tipo 4 prestamos/articulos) come from the new `openRouteCash(branchId)` GraphQL query over `tbl_contabilidad_detalle`, cached in the `route_cash` table (migration 10→11) and refreshed when branch data, "Actualizar cartera" or "Sincronizar ahora" run online.
- Payment methods: the inline abono, the full abono form and the new-card form show a «Método de pago» picker (Efectivo by default, plus one chip per bank account the office authorized for this branch, from `bankAccounts`, cached in the `bank_accounts` table — migration 11→12, which also adds `payments.bankAmount` and `credits.bankFunded`; 12→13 adds the holder name and NIT/CC). Picking a bank shows type, number, holder and NIT/CC so the customer knows where to transfer, then asks how much went through it (blank = all; less = mixed, the rest cash) and an optional reference, sent as `bancos`. The Caja line then counts only cash: `R` = abonos − transfers, `C` = credits − bank-paid, and shows `Banco: +received −paid` apart. The picker is hidden when the company has no bank accounts. If the transfer is bigger than the abono, the picker shows «Transfirió de más: le devuelves $X en efectivo» with a checkbox; only after confirming does the abono travel with `vuelto`, and the Caja discounts that cash. Editing an abono also shows the picker with a «Sin cambios» chip: untouched it keeps the existing split, «Efectivo» clears it, and choosing a bank re-sends it — the way to fix a typed-wrong abono or transfer.
- Notices are no longer red text above every screen: they show as a brief snackbar (with a "Logs" shortcut) and are stored in the encrypted `activity_log` table (migration 9→10), pruned to the last 7 days and at most 300 entries per account and wiped on logout. Sync pauses and failed payment confirmations are logged too. The Cola screen has two tabs: **Cola** and **Logs**. Queue cards show what the collector knows — customer name, card concept/value/balance, amount, date/time and `str_tipo str_codigo` — with plain status labels ("Esperando envío", "Enviando…", "Rechazado por el servidor"); operation IDs and entity IDs are not shown, and the raw server state for conflicts/rejections is behind "Ver datos técnicos (soporte)".
- The portfolio uses a two-tap card: the first tap moves the pointer to that card (outlined border plus an "Aquí vas" marker) and the second tap on the same card expands the payment and manually confirmed remaining-balance fields beside the last movement. Saving keeps the collector on the route, closes the form and shows a brief local-pending notice; server confirmation or rejection is shown later without treating a local save as approval. "Ver todos los movimientos / editar abono" opens the existing detail screen, and the ⋮ menu keeps "Abonos e historial completo" to open that same full-history payments screen for the "Aquí vas" card. The portfolio uses a lazy list with stable card IDs, groups cached payments and operation statuses per card, and refreshes only the affected card after an abono. The branch portfolio and its customers are read in two local queries rather than one query per card. The pointer survives screen changes, configuration changes, and process death, and returning from another screen scrolls the pointed card into view. The pointer is cleared when the branch changes, when the pointed card leaves the cache, and on logout.
- "Crear tarjeta" on the pointed card, or "Crear otra tarjeta" on the open card, first opens a human credit-assessment screen. It immediately shows **all locally saved cards and movements for that customer in the selected branch**, including cancelled cards; online it looks up the customer's document in the authorized branch and requests each card's full payment history. An unsuccessful lookup or incomplete history is stated explicitly, never presented as a complete check. Neither lookup nor device data automatically approves the customer: the employee chooses whether to open the form, and the server still validates credit limits and the open route at submission. Data belonging to other branches is not exposed by this branch-scoped API.
- The new-card form defaults to **After** the selected card and offers **Before/After**. It computes a provisional `float_item` against the locally cached route, tolerating legacy duplicate positions; the queued operation carries the reference card and placement. On synchronization the server calculates the definitive position from the locked branch route. If adjacent positions coincide or have no representable FLOAT gap, it renumbers that branch's cards in their existing order; the existing card-update triggers emit change events for every moved card, so other devices receive the new positions. `Valor cuota` displays `valor a pagar / plazo` rounded to two decimals without allowing manual edits. Only articles show description and initial payment; loans show either insurance value, receipt number plus value, or neither, following the branch's cached `extraCharge`. If that configuration or the receipt sequence is unavailable offline, creation is blocked rather than guessing. Receipt number displayed offline is provisional: the server advances the locked branch counter when applying the card, avoiding collisions with other phones. The server supplies route, creator and timestamps; geolocation is not an existing field of this card table.
- The initial debt (`dec_resta`) is the **total payable** (`dec_valor`), not the cost/capital (`dec_prestamo`); if an article has an initial payment, that payment reduces the debt. Both local optimistic creation and queued-operation replay use this rule. Editing the cost never overwrites the current debt.
- As in the PHP cartera, when the cost/capital of a new card exceeds available cupo, the server raises the customer's maximum in the same transaction for Super Administrador, the branch office administrator or an employee with `editar cliente` / `editar maximo del credito` permission in that branch. Without authorization it rejects the operation with a Spanish explanation; the existing inactive-customer rule still applies. The APK also translates older English cupo rejections already in its queue.
- Creating a customer requires an online document lookup against the company using the configured person-document types. If the customer already exists, the app opens their branch record when accessible instead of duplicating it; if only the person exists, their details prefill the form and the server reuses that person. "Máximo cupo que apruebo" is checked against the authenticated employee's `dec_max_credito` (except Super Administrador), with a fresh server check on sync. The same ceiling applies when an authorized employee raises the customer's limit while creating a card or editing the customer's approved maximum; an office administrator is not exempt from this monetary ceiling.
- Both "Crear cliente" and "Buscar cliente por documento" use a server-loaded menu of person-document types and the same lookup. If the customer exists in the company, the employee reviews their cards, balances, comments and complete payment history **in the authorized branch**, then uses "Apto" to open the existing new-card form (or opens the customer without duplicating them). The reference for route ordering is always the portfolio card marked "Aquí vas", even when it belongs to another customer and the searched customer has no cards in this branch. That reference must be confirmed by the server; the server sets the definitive position next to it. If there is no customer in the company, "Apto" opens the new-customer form with the searched identity; an existing person without a customer is prefilled. Employees with "nueva tarjeta" permission can search existing company customers in their branch even without "crear cliente"; only employees with "crear cliente" can open the registration form. A missing or partial server response never enables approval. New-card approval requires a completed online history consultation and an active connection; saving the card checks the server connection again before placing a provisional operation in the queue. Previously rejected local drafts remain available for explicit retry or discard.
- Additional interest changes a card to `refinanciada`, so "Agregar interés" is unavailable while its locally known status is `created` or `entregando`. The app rechecks before queuing and the server checks the locked card when applying the operation, including after offline delays. The PHP cartera also rejects the operation in those states.
- A fixed bottom bar replaces the stacked buttons that used to scroll away with the list: `‹`/`›` step the pointer through the currently filtered portfolio (disabled at both ends and outside the cartera, and they never open the card), an up/down-arrow button opens the queue with its unresolved-operation count, a starred-cards button opens the marked list with its own counter, a boxed number shows the pointed card's position and returns to the cartera with the pointer in view, and an overflow menu carries the other actions. The redundant queue button above "Cartera guardada" is removed. The bar is hidden on the login and branch pickers.
- On the payments screen the overflow menu also carries the seven card actions (edit, change status, reorder, discount, interest, refresh payments, delete), all bound to the card currently open, leaving only "Registrar pago" on the screen itself.
- Any portfolio card can be starred to revisit it later. Marks are stored only on the device, never sent to the server, and are removed on logout and when another branch's cache is purged. Tapping a bookmark only returns the pointer to that card in the cartera; opening its payments still requires a deliberate tap on the card, because the pointer is armed only by tapping the card itself (arrows and bookmarks leave it disarmed).
- The payments screen lists each movement as abono, resta, formatted date/time, description and state. `createdAt` arrives as epoch milliseconds (GraphQL's String coercion of a MySQL `DATETIME`), so the UI parses that, plain SQL datetimes and ISO instants before formatting; amounts use Colombian grouping. "Resta" is not sent by the server and is not stored in `tbl_descripcion`: it is rebuilt on the device from the card's current balance by undoing each newer movement, and the screen says so. A locally created payment is stamped with the device clock so it sorts and displays before the server confirms it.
- Editing or deleting a payment is only offered while it is still `created`; settled or handed-over movements show "Ya liquidado · no se puede editar ni eliminar" instead of dead buttons. "Eliminar crédito" is likewise disabled unless the card itself is still `created`. The server enforces the same rule for both `UPDATE_PAYMENT` and `DELETE_PAYMENT`, matching the legacy PHP, which already deleted only `str_estado='created'` rows.
- Switching the selected branch clears the previous branch's cached customers, cards, payments, and cursor. Still-pending operations stay bound to their original branch until acknowledged or deliberately discarded.
- Background synchronization can be turned off. The sync screen holds the on/off switch, the interval field (disabled while off), a pending-operations counter, and a "Sincronizar ahora" button that pushes the queue and then pulls server changes on demand. With the switch off no periodic work is scheduled, not even after choosing a branch; the button and the per-save push still run.
- Saving an inline payment keeps the collector in the portfolio instead of waiting for the server to confirm. The movement is written to the local queue and shown with its pending marker; terminal confirmation or rejection refreshes that card and displays a brief notice. The queue remains available for investigating or resolving refusals. Payments entered from the detailed movement screen still return to that screen.
- Any open card offers "Crear otra tarjeta a este cliente", on the card screen and in the overflow menu, gated by the same `nueva tarjeta` permission as the legacy `views/cartera.html` button. The customer, the branch receipt sequence, and the next receipt number are preloaded; the number increments the last one while keeping its zero padding, exactly like `ajax/CarteraAjax.php`. Position is chosen with Primera/Antes/Después/Última chips (the midpoint between neighbours, with ±1.1 jumps at the edges) instead of typing a raw item number, concepto and modo are chips, and utilidad is computed as valor − costo and never typed, matching `dist/scripts/NuevoCredito.js`. The branch receipt sequences are cached in Room (`receipt_sequences`, schema v9) so the form still works offline after one online sync.
- Room is encrypted with SQLCipher. A random database key and the current session/token are AES-GCM encrypted under an Android Keystore AES key; wrapped material and session data are in `noBackupFilesDir`. Android cloud/device backup is disabled for app data.
- Offline changes are durable, account/company/branch-bound queue records with a UUID operation ID. Existing-record edits carry the stored change cursor as `baseVersion` (or an explicitly entered cursor if no local version is known). Customer references are server-assigned integer IDs. Credit IDs are opaque varchar IDs; create-credit sends an app-generated ID that the backend validates and persists exactly.
- `PENDING` and `IN_FLIGHT` remain visibly pending. A record becomes `CONFIRMED` only after the server returns a matching operation ID and an applied/confirmed acknowledgement. Transient network/server errors retry with WorkManager backoff when connected. The same UUID is reused on every attempt.
- A new card rejected by the server remains a **local, unapproved draft**, visibly labelled as such in the portfolio; its apparent balance is not a server-confirmed debt. Once the customer/employee cupo or permissions have been corrected on the server, open **Cola** and tap **Reintentar esta tarjeta después de corregir el cupo** while connected. This explicitly requeues the same operation and card IDs without creating a duplicate card; rejection never triggers an automatic retry. If approval cannot be obtained, **Descartar borrador** removes the local copy instead. Do not uninstall while the queue contains unconfirmed operations.
- Authentication expiration pauses the account queue until a successful online re-authentication. Permission rejection, conflicts, and rejected operations pause automatic sync. A conflict displays the returned server entity (only whitelisted observed fields are retained) and requires the user to deliberately discard the local draft before processing resumes. If the server omits its entity, the app says so and clears the optimistic cached record when the user explicitly discards. Rejected drafts also need an explicit discard. The backend's response and validation are authoritative.
- Logging out removes the account's cached records and queued operations. If unresolved operations exist, the app requires a separate discard confirmation first. Reinstalling the app also removes the device-local key and cache, so unsynced operations are unrecoverable; the UI warns about this.
- **Cuentas del día** (overflow menu) closes the route from the phone, mirroring the web totalizar. It needs internet and an empty queue; with pending operations, no open route, or without the handover permission (Super Administrador, office administrator, or `bloquear` on the branch) it explains why and keeps the button disabled. It lists every movement of the day in plain words (person, amount, branch), totals base, abonos, otro recaudo, créditos and gastos, discounts what came in by bank, and asks only for the counted cash and coins. It then shows «sobra» / «falta» / «cuadrado»; sending it calls `settleRoute` and leaves the route and all its records in `entregando`. Movements that do not move cash (intereses, descuentos, office entries and `salida-contabilidad`) are listed but greyed out and excluded from the total.

This stage excludes expenses and collector dispatch; those remain in PHP.

## Operation form and payload coverage

All exposed queue operations use typed fields and strict backend key names from `src/services/validation.ts`; payloads do not include `companyId` or `branchId`, which are bound by the authenticated operation input:

- Customer create/update sends `nombres`, `apellidos`, `sexo`, `fechaNacimiento`, `tipoDocumento`, `numeroDocumento`, `telefono`, `email`, `ocupacion`, `notaPersona`, `departamento`, `ciudad`, `barrio`, `calle`, `maxCredito`, `apodo`, `notaCliente`, `estadoCliente`, and `fiadorPersonaId`. Edits require an integer server customer ID. A locally created customer cannot be edited or referenced by a credit until its create operation is acknowledged, because `idcliente` is an integer and the server allocates it.
- Credit create sends `idtarjeta` matching `entityId` (opaque varchar, not an integer), integer `idcliente`, `idventa`, `concepto`, `valor`, `modo`, `plazo`, `prestamo`, `descripcion`, `cuotaInicial`, `item`, `utilidad`, `adicionalNumero`, `adicionalValor`, `tipoComprobante`, `serie`, `numero`, `nota`, `obligacion`, and `detalleDocumentoSucursalId`. It does **not** send a route ID; the backend chooses the open route. The branch document-sequence ID comes from the cached `receiptSequences` query; the form refuses to save without it. Credit update, terms, status, and reorder use their exact backend keys.
- Payment create uses the credit's opaque ID as mutation `entityId`; a generated `iddescripcion` identifies the new payment in the strict payload. The user enters a positive amount and the mapper sends a negative `abono`, matching the PHP/backend balance convention. Payment update also sends a negative `abono` and `descripcion`; delete has an empty object payload.
- Credit/payment delete and comment delete show a separate confirmation before queueing.
- Discount sends a negative `amount` (the legacy PHP form negates discount input); interest sends a positive amount plus integer `plazo`. Both accept optional `descripcion`.
- Comment create/update/delete use typed forms with `idcliente`/`comentario`/`tipo` and the strict update/delete payloads. Alert upsert takes icon, color, subject, and alert text and packs them as `icon/,color/,subject/,message`, matching `SaveOrupdateAlerta`; subject/body `/,` delimiters are stripped like the PHP source. Existing comment/alert IDs and a base cursor can be entered where needed.

Forms perform type, range, length, mode, and required-field checks for the payload contract. Permissions, open-route/document-sequence availability, balance, duplicate records, authorship, and all business rules remain server-authoritative. Permission rejections are stored as `REJECTED`, shown with the server message, and stop automatic retry. Conflicts retain a whitelisted server-current record when returned and require deliberate discard/resolution before the queue resumes.

The credit create form requires a customer ID already assigned by the server; it does not queue a credit against a temporary customer ID. Route selection is omitted because the backend assigns the current open route. Route discovery and document-sequence discovery/picking (the sequence ID is currently entered by the user) remain usability follow-up work. Existing comments/alerts are not independently listed by the app, so users must provide an ID to update/delete an existing record; the server validates ownership and scope.

`UPDATE_DOCUMENT` is not offered as a separate operation; document type/number are included in the typed full customer edit form. Cash close/reconciliation, expenses, and collector dispatch remain in PHP and are not exposed in Android.

Logging out while unresolved queue operations exist presents an explicit discard confirmation before deleting that account's local cache. The device unlock prompt is local-only and does not authenticate to the server.
